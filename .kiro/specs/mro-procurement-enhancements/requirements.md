# Requirements Document

## Introduction

This document covers five incremental enhancements to the ZE Electronics PHP/MySQL procurement system (XAMPP). Each enhancement closes a gap identified between what the system currently does and what each role needs. The five feature areas are:

1. **PO Splitting — Buyer view**: The Buyer needs a dedicated page to view, filter, and track the split Purchase Orders that the Admin generates via `Admin/HTML/suppliers.php`.
2. **Supplier Management & Bidding — completeness**: The Admin's existing Suppliers & PO Splitting page needs minor behavioural gaps closed (duplicate-bid guard, bid-deletion safety, PO status updates) so the generated POs are fully usable by the Buyer.
3. **MRO Budget Categorization**: The Create Request form already sends `category` and `subcategory` to the database, but `dept_budget_id` is never populated and budget is not deducted per MRO category on Finance approval. Finance needs a per-category budget breakdown view.
4. **Withdrawal / Refund — extension**: Requestors can currently only withdraw PRs with `buyer_status = 'purchased'`. The withdrawal must also be available for approved PRs that have not yet been purchased, and refunds must credit back the correct MRO department budget.
5. **Withdrawal Oversight — Admin**: Admin needs read-only visibility into all withdrawal requests with full audit history.

## Glossary

- **PR**: Purchase Request — a record in `purchase_requests`.
- **PO**: Purchase Order — a record in `purchase_orders` generated by the Admin after bidding.
- **Requestor**: A system user with role `REQUESTOR` who creates PRs.
- **Buyer**: A system user with role `BUYER` who processes payment against finance-approved PRs.
- **Admin**: A system user with role `ADMIN` who manages users, suppliers, bidding, and budgets.
- **Finance**: A system user with role `FINANCE` who approves/rejects budget spend and withdrawal requests.
- **MRO**: Maintenance, Repair, Operations — the three department budget categories stored in `department_budgets`.
- **Split PO**: One of potentially multiple `purchase_orders` rows generated from a single PR when bids are split across suppliers.
- **dept_budget_id**: Foreign key on `purchase_requests` referencing the relevant row in `department_budgets`.
- **buyer_status**: Column on `purchase_requests`; values: `pending_payment`, `purchased`.
- **withdrawal_status**: Column on `purchase_requests`; values: `none`, `requested`, `approved`, `rejected`.
- **Supplier_Bid**: A row in `supplier_bids` linking a supplier, a PR, a unit price, a delivery date, and an allocated quantity.
- **Finance_Budget**: The `finance_budget` table row (id=1) representing company-wide totals.
- **Department_Budget**: A row in `department_budgets` for Maintenance, Repair, or Operations.

## Requirements

### Requirement 1: Buyer — View and Track Split Purchase Orders

**User Story:** As a Buyer, I want to see all Purchase Orders that have been generated by the Admin so that I can track which items have been ordered, from which suppliers, and when they are expected to arrive.

#### Acceptance Criteria

1. THE Buyer_PO_View SHALL display a dedicated navigation link labelled "Purchase Orders" in the Buyer sidebar that links to a new page `Buyers/HTML/buyer_pos.php`.
2. WHEN the Buyer navigates to the Purchase Orders page, THE Buyer_PO_View SHALL fetch and display all rows from `purchase_orders` joined with the originating PR's `pr_number`, `mpn`, `category`, and `requestor_name`.
3. THE Buyer_PO_View SHALL display the following columns for each PO: PO Number, PR Number, Supplier Name, MPN, Quantity, Unit Price, Total Amount, Currency, Delivery Date, and Status.
4. WHEN a PO has `status = 'Issued'`, THE Buyer_PO_View SHALL display the status badge in blue.
5. WHEN a PO has `status = 'Received'`, THE Buyer_PO_View SHALL display the status badge in green.
6. WHEN a PO has `status = 'Cancelled'`, THE Buyer_PO_View SHALL display the status badge in red.
7. THE Buyer_PO_View SHALL provide a filter control that allows the Buyer to filter the list by PO status (`All`, `Issued`, `Received`, `Cancelled`).
8. THE Buyer_PO_View SHALL provide a search input that filters results by PO Number or PR Number, updating the visible rows without a full page reload.
9. WHEN the Buyer clicks "Mark as Received" on an `Issued` PO, THE Buyer_PO_View SHALL send a POST request to a backend endpoint that updates `purchase_orders.status` to `'Received'` for that PO.
10. WHEN the status update succeeds, THE Buyer_PO_View SHALL refresh the row in place and display a success notification without reloading the full page.
11. IF the status update fails, THEN THE Buyer_PO_View SHALL display an error notification with the server-returned message.
12. WHEN there are no Purchase Orders in the database, THE Buyer_PO_View SHALL display an empty-state message: "No purchase orders have been generated yet."

### Requirement 2: Admin — Supplier Management & Bidding Completeness

**User Story:** As an Admin, I want the Suppliers & PO Splitting page to guard against data-entry errors and correctly reflect PO lifecycle changes so that the generated POs are reliable.

#### Acceptance Criteria

1. WHEN the Admin attempts to add a bid for a supplier that already has a bid on the same PR, THE Supplier_Bid_Manager SHALL return an error response indicating the duplicate and SHALL NOT insert a second row into `supplier_bids` for that `(pr_id, supplier_id)` pair.
2. WHEN the Admin attempts to delete a supplier that is referenced by at least one row in `supplier_bids` or `purchase_orders`, THE Supplier_Manager SHALL return an error response and SHALL NOT delete the supplier record.
3. WHEN the Admin generates split POs for a PR, THE Supplier_Bid_Manager SHALL update `purchase_requests.buyer_status` to `'pending_payment'` for that PR if it is not already set.
4. WHEN the Admin generates split POs for a PR, THE Supplier_Bid_Manager SHALL set `purchase_requests.status` to remain `'approved'` and SHALL NOT alter it to any other value.
5. WHEN all POs for a given PR have `status = 'Received'`, THE Purchase_Order_Manager SHALL update `purchase_requests.buyer_status` to `'purchased'` for that PR.
6. THE Supplier_Manager SHALL display the count of active suppliers next to the "Suppliers" tab label.
7. WHEN the Admin views the Purchase Orders tab, THE Purchase_Order_Manager SHALL allow the Admin to update a single PO's status between `Issued`, `Received`, and `Cancelled` via an inline control on each row.

### Requirement 3: MRO Budget Categorization

**User Story:** As a Requestor, I want my purchase request to be linked to the correct MRO department budget so that Finance and Admin can monitor spending per category. As a Finance user, I want to see a per-category budget breakdown so that I can monitor and control MRO spending.

#### Acceptance Criteria

1. WHEN a Requestor submits a Create Request form with a selected `category` value of `Maintenance`, `Repair`, or `Operation`, THE Request_Submitter SHALL look up the matching row in `department_budgets` by `department_name` and store its `id` in `purchase_requests.dept_budget_id`.
2. WHEN `category` is `Operation`, THE Request_Submitter SHALL match against the `department_budgets` row with `department_name = 'Operations'` (plural form used in the database).
3. WHEN Finance approves a PR (`finance_approvals` insert with `status = 'approved'`), THE Finance_Budget_Manager SHALL deduct `purchase_requests.total_amount` from the `department_budgets` row referenced by `purchase_requests.dept_budget_id` by decrementing `spent_amount` and `remaining_amount` accordingly.
4. IF `purchase_requests.dept_budget_id` is NULL at the time of Finance approval, THEN THE Finance_Budget_Manager SHALL log a warning and SHALL still complete the Finance approval without deducting any department budget.
5. WHEN the Finance user navigates to `finance/HTML/finance-budget.php`, THE Finance_Budget_View SHALL display a section titled "MRO Budget Breakdown" showing three cards — one each for Maintenance, Repair, and Operations — each displaying `allocated_amount`, `spent_amount`, and `remaining_amount` from `department_budgets`.
6. WHEN the Finance user navigates to `finance/HTML/finance-budget.php`, THE Finance_Budget_View SHALL display the existing company-wide totals (Total, Spent, Remaining) alongside the MRO breakdown without removing or replacing the current layout.
7. THE Finance_Budget_View SHALL calculate and display a utilization percentage for each MRO category as `(spent_amount / allocated_amount) * 100`, displaying `0%` when `allocated_amount` is zero.
8. THE Admin_Budget_View on `budget_categories.php` SHALL continue to display the same MRO breakdown and allocation form without behavioural change; no modifications to Admin budget functionality are required.

### Requirement 4: Withdrawal / Refund Extension

**User Story:** As a Requestor, I want to be able to request a withdrawal for an approved PR that has not yet been purchased (in addition to the existing purchased case), so that I can cancel a requisition before the Buyer processes it. As a Finance user, I want withdrawal approvals to automatically credit back the correct MRO department budget.

#### Acceptance Criteria

1. WHEN a PR has `status = 'approved'` AND `buyer_status = 'pending_payment'` AND `withdrawal_status = 'none'` AND no PO rows exist in `purchase_orders` for that PR, THE Requestor_Withdrawal_Form SHALL display a "Request Withdrawal / Refund" button for that PR on `my-requests.php`.
2. WHEN a PR has `buyer_status = 'purchased'` AND `withdrawal_status = 'none'`, THE Requestor_Withdrawal_Form SHALL also display the "Request Withdrawal / Refund" button (existing behaviour preserved).
3. WHEN a Requestor submits a withdrawal request for an approved-but-not-yet-purchased PR, THE Withdrawal_Request_Handler at `Requesitor/PHP/request_withdrawal.php` SHALL accept the request, insert a row into `pr_withdrawals`, and set `purchase_requests.withdrawal_status = 'requested'` within a single database transaction.
4. WHEN Finance approves a withdrawal for a PR with `buyer_status = 'purchased'`, THE Finance_Withdrawal_Approver SHALL deduct `pr_withdrawals.amount` from `finance_budget.spent_budget`, add it back to `finance_budget.remaining_budget`, and additionally credit back `department_budgets.spent_amount` and `department_budgets.remaining_amount` for the department referenced by `purchase_requests.dept_budget_id`.
5. WHEN Finance approves a withdrawal for a PR with `buyer_status = 'pending_payment'`, THE Finance_Withdrawal_Approver SHALL add `pr_withdrawals.amount` back to `department_budgets.remaining_amount` and reduce `department_budgets.spent_amount` for the referenced department, and SHALL additionally set `purchase_requests.buyer_status = 'pending_payment'` (unchanged) and `purchase_requests.status = 'approved'` (unchanged).
6. WHEN Finance approves a withdrawal for a PR where `purchase_requests.dept_budget_id` is NULL, THE Finance_Withdrawal_Approver SHALL complete the approval and credit back `finance_budget` only, logging a warning about the missing department budget link.
7. WHEN Finance approves a withdrawal for a PR that is `approved` and `pending_payment`, THE Finance_Withdrawal_Approver SHALL insert a `budget_transactions` row with `transaction_type = 'refund'` and the relevant `department` name.
8. WHEN a withdrawal is approved, THE Finance_Withdrawal_Approver SHALL update `purchase_requests.withdrawal_status = 'approved'` and `pr_withdrawals.status = 'approved'` within the same transaction.
9. WHEN a withdrawal is rejected, THE Finance_Withdrawal_Approver SHALL update `purchase_requests.withdrawal_status = 'rejected'` and `pr_withdrawals.status = 'rejected'` within the same transaction.
10. WHILE a withdrawal request is in `status = 'pending'`, THE Requestor_Withdrawal_Form SHALL display a "Withdrawal Pending Review" badge on `my-requests.php` and SHALL NOT display the withdrawal button again.
11. IF a PR already has an active withdrawal in `status = 'pending'`, THEN THE Withdrawal_Request_Handler SHALL reject a second submission with an error message: "A withdrawal request is already pending for this PR."

### Requirement 5: Withdrawal Oversight — Admin

**User Story:** As an Admin, I want to view all withdrawal requests submitted by Requestors and their Finance review outcomes so that I can maintain an audit trail and investigate disputes.

#### Acceptance Criteria

1. THE Admin_Withdrawal_Oversight page SHALL be accessible at `Admin/HTML/admin_withdrawals.php` and SHALL be protected so that only users with `role = 'ADMIN'` can access it.
2. THE Admin_Withdrawal_Oversight_View SHALL display all rows from `pr_withdrawals` joined with `purchase_requests` (for `mpn`, `category`, `subcategory`) and with `users` for the reviewer's name.
3. THE Admin_Withdrawal_Oversight_View SHALL display the following columns: PR Number, Requestor Name, MPN, Category / Subcategory, Amount, Currency, Reason, Submitted Date, Status, Reviewed By, and Reviewed At.
4. THE Admin_Withdrawal_Oversight_View SHALL display status badges using the same colour scheme as the Finance view: `pending` in yellow, `approved` in green, `rejected` in red.
5. WHEN Admin views a rejected withdrawal, THE Admin_Withdrawal_Oversight_View SHALL display the `rejection_reason` inline beneath the status badge.
6. THE Admin_Withdrawal_Oversight_View SHALL provide a status filter (`All`, `Pending`, `Approved`, `Rejected`) that filters the displayed rows without a full page reload.
7. THE Admin_Withdrawal_Oversight_View SHALL provide a date-range filter (from date, to date) that limits displayed rows to those with `pr_withdrawals.created_at` within the specified range.
8. THE Admin sidebar on `Admin/HTML/ZE-Electronics.php` and all other Admin navigation pages SHALL include a link labelled "Withdrawals" pointing to `Admin/HTML/admin_withdrawals.php`.
9. THE Admin_Withdrawal_Oversight_View SHALL be read-only; THE Admin SHALL NOT be able to approve or reject withdrawals from this page.
